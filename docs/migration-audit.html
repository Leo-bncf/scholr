Is the migration done?

No — and here is exactly what's missing

base44 is fully gone from the frontend: no SDK, no dependency, no hot-linked assets. The database, RLS, storage, auth and the deployment pipeline are all live and tested. That part is genuinely finished.

Ten server functions are not ported, so the features behind them are inert. They fail with a clear message rather than silently — but they don't work:

Three credentials block already-written code

SMTP — invitations create the record and return an accept link, but send no email. Stripe keys + webhook secret — all three billing functions return 503. Google OAuth redirect URIs — still pointing at base44. None of these need code; they need values.

What the audit found

Ordered by how much damage each would have done

RLS translation dropped tenant scoping on 14 tablesFixed

base44 conditions are an implicit AND of their keys, with $or as one key among them. My first translator returned on seeing $or and discarded its siblings — including school_id. A school admin could read other schools' grades. The same bug dropped 8 visible_to_student gates, exposing unpublished grades to students, and 5 created_by rules, hiding teachers' own grades from them.

A write policy that granted read accessFixed

Policies written FOR ALL … USING (true) also cover SELECT, and Postgres policies are OR'd. The "anyone may submit this form" rule therefore handed out reads: anonymous visitors could list the demo-request leads, and any signed-in user could read every support ticket and error log.

Three separate holes in the invitation flowFixed

base44's acceptInvitation looked rows up by enumerable id and never checked the invitation's email against the person redeeming it — anyone with a token could claim a role meant for someone else, including school_admin. createAccountFromInvitation took the email from the request body, so a leaked token could create an attacker-controlled account holding the invited role. And sendInvitation authorised by trusting any of four differently-spelled role fields on the user object.

Every function response was being read wrongFixed

base44 wrapped responses in { data }. The replacement returns the body directly, so 59 result.data.success checks across 24 files were reading undefined and silently taking the failure branch. Account creation, billing redirects and Google checks would have reported failure while succeeding on the server.

A column rename that failed silentlyFixed

base44's created_date doesn't exist in the new schema. 168 references across 45 files were evaluating to undefined, so date filters and growth charts quietly returned nothing rather than erroring.

Security theatre removedFixed

src/lib/rls.js, useRLS and RLSProvider filtered records in the browser after fetching them — no protection at all, since the API had already returned the rows. Nothing consumed the context. Deleted, and the documentation rewritten to describe the real Postgres model.

Two buttons that never workedFixed

The frontend called createStripeCheckout and generateReportPDF. Neither exists in base44 either — the real names are createCheckoutSession and exportReportPDF. These were broken before the migration started.

Duplicate attendance records were possibleFixed

Registers get re-taken. With no unique key on (class_id, student_id, date), a correction wrote a second row and every attendance rate computed from it drifted. Existing duplicates collapsed, index added.

The ground to build on

One command tells you whether anything is broken

Every check below runs against the real stack, not a mock. npm run verify chains them.

CommandProvesNow
npm run lintNo unused or broken imports0 errors
npm run verify:rlsCross-tenant reads and writes are refused; unpublished grades stay hidden10/10
npm run verify:functionsInvitation round-trip, and every authorisation rule around it31/31
npm run verify:dataEvery column the app selects exists in the database61/61

verify:data is the one worth understanding: the data modules hand-write their column lists, and a typo there is neither a build error nor a test failure — it's a 400 the first time a user opens that screen. It asks Postgres directly.

What I'd do next

In order

  • Supply the three credentials. SMTP, Stripe, Google. Written code is sitting idle behind them, and invitations are the first thing a real school touches.
  • Set up backups. Schedual has age-encrypted dumps, WAL shipping and a weekly restore drill. Scholr has none. Trivial at 7 rows, painful to retrofit under load, unforgivable after a school's data arrives.
  • Port the remaining ten functions, or delete the features. Demo seeding and Google Drive may not be worth carrying.
  • Tighten parent visibility. visible_to_parent = true currently lets any school member read that grade, not only the linked parent. base44's semantics, preserved deliberately — but it should become an EXISTS against parent_student_links before real parents log in.
  • Make submissions.submit atomic. Demoting the old version and inserting the new are two statements; a failure between them briefly reads as "not submitted".
  • Retire the where() escape hatch gradually. It exists so the migration could finish; each call site that gets touched should grow a named query instead.
